# ADR 0009 · 数值外置与版本化存档

日期：2026-11-20
状态：已采纳

## 背景

前面几步把玩法立起来了，但所有平衡数字还写死在 `src/core/config.js` 里：想调小怪血量就得改代码、重新构建、等 Pages 重建。同时每次刷新页面所有进度归零——没有跨局的东西，玩家第二天回来没有任何"我上次到哪了"的线索。

## 决定

1. **数值外置到 `web/data/balance.json`**
   只外置"能调的数"：玩家/小怪/Boss 的攻击、血量、速度、预警时间，掉落概率，房间怪数上下限。结构常量（`TILE`、`COLS/ROWS`、地牢网格）仍留在代码里——那是架构，不是数值，混在一起会让人以为改个数字就能改房间大小。
   `src/systems/data.js` 用白名单把 JSON 打散写回 `CFG`，只接受有限数字，缺字段就保留默认；房间怪数上下限配成 5..3 时会自动夹回。
2. **每次启动先读 JSON，读不到就用构建期内嵌副本**
   Boot 里 `load.json()` 拉 `web/data/balance.json`；`file://` 双击或断网时加载失败，自动退回 `assets.js` 里那份构建期快照，单文件版行为一致。
3. **版本化存档只存跨局的东西**
   `src/systems/save.js`，`localStorage` 键 `na.save`，v2 结构：`coins / kills / runs / wins / bestRoom / muted`。局内血量、当前房间、掉落**不进档**——每局该从零开始。
   - 读写包 `try/catch`；解析失败时把坏档另存 `na.save.broken` 再按新档处理，不崩游戏。
   - `v1 → v2` 只做补字段，不丢弃旧数据。
   - `?reset` 清档，方便换机器/复现。
4. **写盘时机只在"一局结束"**
   死亡或通关时一次性提交，`commitRun()` 有幂等标记，避免同一局重复记账；金币累加、击杀累加、`bestRoom` 取大值、通关单独计数。静音开关即时写盘（那是设置，不是进度）。

## 实测

| 项 | 结果 |
|---|---|
| 改 JSON 免构建 | 把小怪血量 6→12、金币掉落 45%→100%，**不重新构建**，刷新后 `CFG.enemyHp=12`、`coinChance=1` |
| 应用条数 | 一次应用 26 个字段，来源标记 `json`（读不到时才标 `embedded`） |
| 死亡写档 | 清 4 怪后死亡 → `{v:2, kills:4, bestRoom:1, runs:1}` |
| 刷新续档 | 同一档读到 `kills:4`，`runs` 变 2（每次启动算一局） |
| `?reset` | 全部归零、`runs` 从 1 重新开始 |
| v1 迁移 | 旧档 `{v:1, coins:7, kills:3}` → `{v:2, coins:7, kills:3, …}`，数据不丢 |
| 坏档 | 存 `'{oops'` → 当新档继续跑，并留下 `na.save.broken` 备份 |

## 代价与边界

- 线上改 `balance.json` 会受 CDN 缓存影响，通常要几分钟才生效；要"秒生效"得加版本号查询串或换配置服务。
- 存档只有本机 `localStorage`：换浏览器/清缓存就没了；要做真正的账号级存档得接后端（P3 叙事层再考虑）。
- `runs` 按"每次启动/重开"计，所以刷新页面也算一局；这个口径对"平均一局多长"的统计不严谨，当作玩家侧进度看没问题。
- 数值白名单是手写的，新增字段要同时改 `data.js` 和 `balance.json`，漏了会静默不生效（启动日志里 `window.__balance.applied` 能看到实际落了哪些）。
