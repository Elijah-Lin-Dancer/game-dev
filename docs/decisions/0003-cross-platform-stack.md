# 0003 跨端策略、分辨率与技术栈

- 状态：已定稿（原型 A 已验证）
- 时间：2026-11-19
- 上游：[0002 主美术](0002-primary-art.md)

## 决策

| 项 | 决定 |
|---|---|
| 首期形态 | **Web App**（单文件 HTML，双击或任意静态服务可运行） |
| 技术栈 | **Phaser 3.80.1**，本地 vendor 后内联，不依赖 CDN |
| 逻辑分辨率 | **短边固定 360**：横屏高 360、宽随比例；竖屏宽 360、高随比例；长边上限 800 |
| 呈现方式 | `Scale.NONE` + 自行 contain：按比例缩放居中，超宽/超高留黑边，不拉伸 |
| 输入 | 键盘（WASD/方向键）+ `Pointer Events`（鼠标、触摸统一），触屏为虚拟摇杆 |
| 素材 | 内联为 data URI，避免 `file://` 跨域限制 |

## 理由

1. **Phaser 覆盖了最费工的部分**：图集/动画/相机/输入/循环。素材是逐帧 PNG 条带，Phaser 的 spritesheet + anims 直接可用；自己写这套基础设施要多花数天，换不来乐趣上的差异。
2. **单文件交付**：Phaser 与素材内联后是 1.17 MB，可以直接发一个文件给别人玩，不需要起服务、不依赖 CDN、不会被跨域卡住。
3. **一套代码两端**：桌面是浏览器窗口，手机是 H5 + 触屏。首期不做抖音小游戏打包，平台适配层等玩法定了再补。
4. **短边固定 360 的理由**：16×16 素材在 360 高的视野里放 2 倍即 32 px，手机与桌面都可读；横向变宽只是多看几格，不影响玩法平衡。

## 实测证据（无头 Chromium，2026-11-19）

| 视口 | 逻辑尺寸 | 画布呈现 |
|---|---|---|
| 390×844（手机竖屏） | 360×779 | 390×844，铺满无黑边 |
| 844×390（手机横屏，旋转后） | 779×360 | 844×390，铺满无黑边 |
| 1200×300（超宽） | 800×360 | 667×300 居中，留边不拉伸 |

功能：WASD/方向键与触屏拖拽均可移动并切换朝向；松手停止；`fps 54–59`；无 `pageerror`。

## 本阶段踩到的三个坑（防重复）

1. **贴图排布是「列=方向，行=帧」**，不是行=方向。`Walk.png` 64×64 → 4 列 × 4 行，帧索引 = `行*4 + 列`；某方向的序列是 `[col, col+4, col+8, col+12]`。误按行读会让四个方向全是正面。
2. **摇杆别先归一化再取长度**：`v.normalize()` 后 `v.length()` 恒为 1，输出被削成 0.015，角色原地不动。
3. **Phaser `Scale.FIT` 在 `resize()` 后仍按旧的 baseSize 算展示尺寸**，旋转后画面变竖条。改用 `Scale.NONE` 自己算 contain 缩放。
